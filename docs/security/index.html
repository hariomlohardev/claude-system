Security model

Install with eyes open — permissions is a disclosure, not a sandbox.

claude-system installs third-party Systems — bundles of CLAUDE.md, skills, agents, commands, hooks, and settings that are executed via Claude Code. Treat installing a System with the same scrutiny as installing any third-party package (npm, pip, Homebrew, etc.).

Permissions are self-declared

Every System's system.json contains a permissions array:

{
  "permissions": ["filesystem:read", "network:read", "shell:exec"]
}
PermissionWhat it signals
filesystem:readMay read files outside the installed System folder
filesystem:writeMay write or mutate files
network:readMay make outbound network requests (fetch, clone)
network:writeMay push data or make mutating network calls
shell:execMay execute shell commands or scripts (hooks, skills)
credentials:readMay access credentials, tokens, or secrets
permissions is declared by the author — you write the honest superset. An empty array [] is valid and means “no special capabilities declared.” additionalProperties: false is enforced, so unknown strings are rejected.

setup.sh contract

If a System ships setup.sh, it must:

  • Include a # WHY: line (or an echo explaining why setup is needed) — this is shown in the claude-system run consent prompt.
  • Be gated by a one-time consent prompt on first claude-system run — never silently executed.
  • Set setupDone in ~/.claude-system/systems.json only after successful setup.sh exit (0); on non-zero, setupDone stays false and next run re-prompts.
  • Declare shell:exec in permissions (enforced by validate.yml cross-check).

Example setup.sh header:

#!/bin/sh
# WHY: installs claude and checks gh auth
echo "Installing…"

claude-system run will show WHY and ask Are you sure you want to continue? (y/N) — no consent, no execution.

Reviewed but not independently verified

  • PR review: Every System PR must pass validate.yml and maintainer review before merge. Reviewers compare declared permissions against actual content in skills/, agents/, commands/, hooks/, and CLAUDE.md (e.g. a System declaring [] but shipping a hook that runs curl | bash will be rejected).
  • Not a runtime sandbox guarantee: The review is human and static. There is no independent runtime verification or sandbox that enforces permissions at execution time. A malicious or compromised System that is merged could do more than it declared.
Do not treat permissions: [] as a proof of safety — treat it as a self-declared and reviewed claim, not a security boundary.

How to read permissions before installing

  1. Inspect the manifest directly — don't trust the display name alone: 
    claude-system info <name>
cat systems/<name>/system.json | jq .permissions
cat systems/<name>/CLAUDE.md
ls -R systems/<name>/skills systems/<name>/hooks
  2. Check the author and links: author.github, repository, bugs.url, homepage.
  3. Read the diff on update: claude-system update will show if a new version adds permissions.
  4. Assume least trust on first install. If you don't need credentials:read or shell:exec, prefer [] or only filesystem:read.

Mental model: permissions is like the permissions list on a browser extension — it's a disclosure you decide to accept, not a capability the platform enforces.

For authors — how to keep trust

  • Declare the honest superset — if any skill, hook, or command could read the network, shell out, or touch credentials, include that permission even if conditional.
  • Don't hide shell:exec if hooks/ or skills/ contain executable code.
  • Minimize — start from [] and justify each addition in your PR description.
  • Never silently grant or escalate — users must see what's being requested before they accept.

Reporting concerns

If you find a System that appears to under-declare permissions, contains obfuscated or unsafe hooks, or exfiltrates data: open an issue in this repository (or the System's bugs.url if it declares one) and label it with the System name. If sensitive, follow the disclosure process in SECURITY.md instead of a public issue.
