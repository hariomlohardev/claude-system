Security

Install with eyes open — permissions is a disclosure, not a sandbox. Reviewed during PR, not verified at runtime.

claude-system installs third-party Systems — bundles of CLAUDE.md, skills, agents, commands, hooks and settings executed via Claude Code. Treat installing a System with the same scrutiny as any third-party package.

Permissions are self-declared

Every system.json contains a permissions array:

{
  "permissions": ["filesystem:read", "network:read", "shell:exec"]
}
PermissionWhat it signals
filesystem:readMay read files outside installed folder
filesystem:writeMay write or mutate files
network:readMay make outbound fetch/clone
network:writeMay push data out
shell:execMay execute shell commands/scripts
credentials:readMay access credentials/tokens
permissions declared by author — honest superset. Empty [] means “no special capabilities.” additionalProperties: false rejects unknown strings.

setup.sh contract

If a System ships setup.sh, it must:

  • Include a # WHY: line — shown in claude-system run consent prompt.
  • Be gated by one-time consent on first run — never silently executed.
  • Set setupDone in ~/.claude-system/systems.json only after exit 0; on non-zero, stays false and re-prompts.
  • Declare shell:exec in permissions (enforced by validate.yml).
#!/bin/sh
# WHY: installs claude and checks gh auth
echo "Installing…"

claude-system run shows WHY and asks Are you sure you want to continue? (y/N) — no consent, no execution.

Reviewed but not independently verified

  • PR review: Every System PR must pass validate.yml and maintainer review. Reviewers compare permissions vs skills/, agents/, commands/, hooks/, CLAUDE.md (e.g. [] + curl | bash → rejected).
  • Not a runtime sandbox: Review is human + static. No independent runtime verification or sandbox enforces permissions at execution.
Do not treat permissions: [] as proof of safety — treat it as a self-declared and reviewed claim, not a security boundary.

How to read permissions before installing

claude-system info <name>
cat systems/<name>/system.json | jq .permissions
cat systems/<name>/CLAUDE.md
ls -R systems/<name>/skills systems/<name>/hooks
  1. Inspect manifest — don't trust display name alone.
  2. Check author and links: author.github, repository, bugs.url.
  3. Read diff on update: claude-system update shows if new version adds permissions.
  4. Assume least trust on first install — prefer [] over credentials:read.

Mental model: like browser extension permissions — a disclosure you decide to accept, not a platform-enforced capability.

For authors — how to keep trust

  • Declare honest superset — if any skill/hook could read network/shell/credentials, include it even if conditional.
  • Don't hide shell:exec if hooks/ has executable code.
  • Minimize — start from [] and justify each addition in PR.
  • Never silently grant or escalate.

Reporting concerns

If you find a System that under-declares permissions, contains obfuscated hooks, or exfiltrates data: open an issue in this repo (or the System's bugs.url) and label it with System name. If sensitive, follow SECURITY.md disclosure instead of a public issue.

Full source is docs/security.md and SECURITY.md on GitHub.
